## 1. Как я понял задачу

**Что сказано в ТЗ**

- MCP-сервер на TypeScript. Каждый проект получает собственную RPG-кампанию: XP, уровни 1–50 с точными титулами,
  класс, статы, квесты, эпики, боссов, достижения и историю. У каждого проекта свой XP; общий профиль разработчика
  только сводит проекты вместе.
- Квесты строятся из реального состояния проекта. Разные проекты получают разные квесты, а доска подстраивается под
  текущие слабые места.
- XP начисляется только после проверки по сигналам проекта (тесты, git diff, сборка, линт, статический анализ, файлы),
  а не потому, что ИИ сказал «готово». Объём кода не награждается.
- Игровое ядро не зависит от MCP, чтобы позже подключить другие интерфейсы.
- Порядок: проектирование → небольшой MVP → проверка на Next.js-магазине и Node.js Telegram-боте → расширение
  (фазы 2 и 3).

**Когда MVP считается готовым**

1. Магазин и бот получают заметно разные доски квестов.
2. Когда проект улучшается, доска перестраивается: например, тестов стало достаточно — вперёд выходят архитектура и
   безопасность.
3. XP нельзя получить без проверяемого улучшения, а большой мусорный коммит не приносит больше XP, чем маленький точный
   фикс.

**Мои допущения (поправь, если не так)**

- В перспективе продукт публичный, как CodeCheck: GitHub, лицензия MIT, английский интерфейс и README. Публикую только
  после твоего «да».
- Анализ детерминированный, без LLM внутри сервера: один и тот же проект даёт одни и те же статы и квесты. Claude читает
  состояние и делает работу, но XP не начисляет.
- Статы — игровые метрики из измеримых сигналов. Формулы описаны в документации, научной точности не заявляем.
- Прогресс (XP, журнал, история) хранится вне анализируемых проектов, у тебя — в `D:\Claude\codequest-data` (путь
  задаётся переменной окружения). В твоих репозиториях ничего лишнего не появляется.

## 2. Правила работы

- Иду по этапам. После каждого: тесты, проверка типов, линт, локальный коммит и короткий отчёт — что сделано, какие
  файлы, реальный вывод тестов, что НЕ проверено. Следующий этап — только после твоего «да».
- Только с отдельного разрешения: установка пакетов, push и публикация, регистрация MCP в Claude Code, изменение
  настроек (status line и т. п.), запуск команд твоих проектов (`npm test`, `pytest` и т. п.).
- TDD: сначала тест на правило, потом само правило. У каждого детектора есть пример с проблемой и чистый пример, на
  котором он молчит.
- Если по ходу вскроется скрытая сложность — останавливаюсь и говорю, а не дотягиваю молча.

Поток данных:

```
проект → сканер → снимок и находки → статы → генератор квестов → доска квестов
                                                                   ↓
правки в коде → автопроверка или кнопка «Проверить квест» → условия выполнены? → XP → уровень → журнал
```

## 4. Фаза 1 — MVP

**1. Каркас.** TypeScript в строгом режиме, Vitest, линтер, структура папок из ТЗ, пустой MCP-сервер с одним
инструментом.
Проверка: тестовый MCP-клиент вызывает инструмент и получает ответ.

**2. Сканер: общие сигналы и JS/TS.** Файлы проекта (через `git ls-files`, без node_modules), языки, зависимости и
фреймворки из package.json, скрипты test/lint/build, тестовые файлы и что они покрывают, TODO/FIXME, история git
(коммиты, часто изменяемые файлы, коммиты-исправления), README и документация, API-роуты Next.js, утечки секретов,
большие файлы, дубли кода, неиспользуемые файлы. Статические сайты без package.json тоже разбираются. У каждой находки —
стабильный отпечаток, чтобы узнавать её между запусками.
Проверка: на фикстурах проблема находится, на чистом примере — нет.

**3. Сканер: Python.** Зависимости из requirements.txt и pyproject.toml; фреймворки (aiogram, python-telegram-bot,
Telethon, FastAPI, Flask, Django); тесты pytest/unittest и что они покрывают; команды pytest и ruff, если они настроены;
неиспользуемые модули по импортам.
Проверка: фикстура Python-бота на aiogram — проблема находится, на чистом примере — нет.

**4. Статы.** Architecture, Testing, Security, Performance, Clean Code, Reliability, Maintainability и счётчики Bugs и
Tech Debt. Формулы общие для всех языков — в `docs/formulas.md`.
Проверка: один и тот же проект даёт одни и те же числа; ручной пересчёт на фикстуре совпадает.

**5. Хранилище и состояние проекта.** Снимок в JSON плюс журнал событий, который только дописывается; атомарная
запись под файловой блокировкой; опознание проекта; общий профиль со списком проектов, у каждого свой XP.
Проверка: перезапуск сервера не теряет прогресс, повреждённый файл восстанавливается из журнала.

**6. XP и 50 уровней.** Точные титулы из ТЗ. Каждый уровень — 500 XP. Награда за квест = базовая по сложности
(Easy 100, Medium 300, Hard 500, Epic 1200) × 0.95^(уровень − 1) × сила проверки (1.0 с запуском тестов, 0.8 без) —
не от числа строк.
Проверка: награды и уровни совпадают с формулой; большой мусорный коммит не выгоднее точного фикса.

**7. Генерация квестов.** Находки превращаются в квесты Easy/Medium/Hard/Epic; мелочь — пачкой; эпики с подзадачами;
вес по слабым статам; адаптация (стат 80 и выше — Easy и Medium квесты этой категории уходят); доска до 8 квестов.
Доменные пакеты: интернет-магазин, Telegram-бот (одинаково для Node и Python), общий.
Проверка: магазин и бот получают разные доски; после того как тесты подтянуты, тестовые квесты уступают место
архитектуре и безопасности.

**8. Проверка выполнения.** У каждого квеста машинно-проверяемые условия: проблема исчезла, модуль на месте, появились
тесты, test/lint/build проходят (`npm test`, `pytest`, `ruff` и т. п.), нет регрессий. При появлении квеста
запоминается «как было». XP — только если выполнены все условия. Подавления (`@ts-ignore`, `# noqa` и т. п.) сами
считаются проблемами.
Проверка: «ИИ сказал, что готово» — 0 XP; удалили файл или тесты — не засчитано; реальный фикс — XP.

**9. MCP-инструменты.** get_project_state, get_project_stats, get_player_level, get_active_quests, get_quest_details,
verify_quest_completion, refresh_project_analysis, set_project_settings; промпты verify_quest (кнопка «Проверить
квест» в меню `/`), quest_board, work_on_quest; ресурсы (HUD, доска, состояние). Автопроверка раз в минуту, пока
открыт Claude Code. Текстовый HUD (Minimal и HUD) и короткие уведомления: «+150 XP · LEVEL UP 17 → 18 · Testing +2».
CLI `codequest`: verify, refresh, hud.
Проверка: тесты через MCP-клиент прямо в процессе.

**10. Приёмка MVP.** Прогон на трёх фикстурах (Next.js-магазин, Node.js-бот, Python-бот на aiogram) и на двух настоящих
открытых репозиториях из ТЗ — магазин и бот (клоны на D, в репозиторий не попадают). С твоего разрешения и только на
чтение — ещё и на твоём боте из `D:\Claude\тг бот`. Сценарий адаптации и полный цикл «квест → реальный фикс →
автопроверка → XP → новый уровень».
Результат: отчёт с досками рядом (магазин и боты получают разные квесты, Node- и Python-бот — похожие «ботовые») и
честным списком того, что не работает.

После приёмки, с твоего «да», — регистрация сервера в Claude Code и живой вызов из новой сессии.

## 5. Фаза 2 — после одобрения MVP

- **Классы** вычисляются по доле проверенной работы в категориях: Architect, Tester, Guardian, Optimizer, Cleaner,
  Builder, Bug Hunter, Researcher; бывают гибриды (Architect + Tester = Test Architect). Влияют на вес квестов, бонусы
  XP, достижения и подсветку статов, но ничего не запрещают.
- **Достижения** — постоянные, за реальные вехи.
- **Боссы** — из скоплений реальных проблем. HP = доля ещё не решённых проблем; связанные квесты снимают HP.
- **История** — таймлайн проекта из журнала событий.
- Инструменты get_project_bosses, get_achievements, get_project_history.

## 7. Решения по умолчанию (любое можно поменять)

- TypeScript и официальный MCP SDK; Node 24 уже установлен.
- Файлы и историю читаю через установленный git, без лишних библиотек.
- Хранение — JSON и журнал JSONL; SQLite — только если упрёмся в скорость.
- Команды проекта (`npm test`, `pytest`, lint, build) при проверке квеста запускаются, только если ты разрешил их для

- Автор коммитов в репозитории — как в CodeCheck: `aleks-fw <aleks-fw@users.noreply.github.com>`, твоя почта в коммиты
  не попадает.
- Пути с пробелами и кириллицей проверяю с первого этапа: пробел есть в пути самого проекта, кириллица — в путях твоих
  проектов (`D:\Claude\тг бот`, `D:\проект 1`).

## 8. Что я заметил в ТЗ

- Примеры XP в ТЗ не сходятся (у 18-го уровня то 14 820 XP, то 8 420). По твоему решению уровни устроены проще:
  500 XP на уровень, а награда за квест падает на 5% с каждым уровнем. Числа из примеров ТЗ не воспроизводим.
- HUD назван одной из главных вещей, но стоит в фазе 3. Поэтому текстовый HUD — уже в MVP, а постоянный показ на экране
  — в фазе 3.
- Тестовый бот в ТЗ на Node.js, а твои настоящие боты — на Python (aiogram, Telethon). Поэтому Python вошёл в MVP.

- Стек MVP — JS/TS и Python. Python-сканер — отдельный этап 3, в приёмку добавлен Python-бот.
