# CodeQuest: switchable language (ru / en)

Date: 2026-09-30. Status: approved by the user (2026-09-30), with `set_language` as a separate MCP tool.

## Goal

The user reads CodeQuest output directly (terminal board, HUD) and through Claude. They want Russian or English, and to switch at any moment without losing progress or restarting anything.

## Decisions

- **One language for everything**, `ru` or `en`, default `en`. Stored in `<CODEQUEST_HOME>/config.json` (`{ "schema": 1, "language": "ru" }`), written atomically. Not per project: the user asked for one switch.
- **Three ways to change it**
  - MCP: new tool `set_language` (`language`: `ru` | `en`; without it, returns the current one). It shows in the client's server panel next to the other tools. The MCP panel of the editor has no place for settings of its own, so a tool is the way in.
  - CLI: `codequest lang [ru|en]` (no argument prints the current one).
  - Board: key **L** toggles and redraws at once.
- **Everything the user sees follows the setting**: HUD, board, quest cards, notifications, check reports, level titles, MCP tool answers, CLI output, USAGE.
- **Fallback**: a key missing in `ru` shows the English text. Nothing breaks when a string is not translated yet.
- **Not translated**: file names, commands, rule ids (`bot/no-timeout`), stat names in machine-facing fields.

## Design

### Catalogs (`src/i18n/`)

- `en.ts`, `ru.ts`: `Record<string, string>` with `{name}` placeholders.
- `t(lang, key, vars?)`, and `plural(lang, n, [one, few, many])` for Russian forms (1 файл, 2 файла, 5 файлов).
- A test walks both catalogs: every key of `en` exists in `ru`, and both use the same placeholders.

### Language reaches the output

Format functions in `src/hud/*` get a `lang` argument (default `en`, so existing callers and tests keep working). `Engine` reads the config on each view and puts `lang` on `ProjectView`; `present.ts` and the tools pass it down. No global state.

### Quest texts

Quests are stored with their English title and description. To switch language later, a quest also stores references: `text: { title: {key, vars}, description: {key, vars} }`. Templates return references; the English string is rendered from the same reference and kept in `title`/`description` (used as a fallback and for old data).

Existing open quests have no `text`. On every cycle the engine refills `text` of open quests from the fresh candidates with the same id (ids are stable), so old boards convert on their own.

`findQuest` matches a quest by number, by English title, or by title in the current language.

### Check reasons and findings

Condition lines (`describeCriterion`) become keys. `CriterionResult.detail` keeps its English text and gains an optional reference; findings get the same for their messages, rule by rule. A reason without a reference stays English (fallback).

## Stages

1. **Mechanism and setting**: config file, `t`/`plural`, MCP parameter, CLI `lang`, board key **L**; translated: HUD, board and card frames, help lines, level titles, notifications, reports, stat labels, tool/prompt texts, USAGE.
2. **Quest texts**: references in templates, migration in the cycle, `findQuest`, condition lines.
3. **Reasons and findings**: check details and finding messages, rule by rule.

After each stage: tests, typecheck, lint, rebuild `dist`, short report with what is and is not translated.

## Testing

- Catalog completeness (keys and placeholders) for `en` vs `ru`.
- Every format function renders both languages; `en` output stays byte-for-byte what it is now (existing tests keep passing unchanged).
- Config: default, write, read, a broken file falls back to `en`.
- MCP tool and CLI command switch the language; the next output changes.
- A quest created in `en` shows Russian after the switch, and back.
- Old state without `text` still renders, and gets `text` after a cycle.

## Not in this change

More than two languages (the catalog shape allows them), per-project language, translating the spec and docs, translating the analyzer's internal logs.
