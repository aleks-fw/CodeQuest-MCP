# CodeQuest MCP — этап 9: движок, MCP, HUD, автопроверка, CLI

Спек §2.2–2.3, §9. Ветка `stage-9`. Пишу и проверяю сам, без субагентов. Три части, у каждой свои коммиты и `npm run check`.

## Часть A — движок (`src/engine/`) — готова

- `cycle.ts` — один сценарий под блокировкой (§2.2): кэш по ключу изменений → анализ (`analyzeWithContext`) → команды
  (только нужные, не чаще раза на ключ) → проверка квестов → XP, уровни, события → доска → журнал, затем состояние.
  Находка `generic/failing-tests` создаётся из красного прогона тестов (сканер её не знает).
- `index.ts` — класс `Engine`: очередь операций на проект, `view` (обновляет, а при идущей операции отдаёт сохранённое
  состояние с `busy`), `refresh`, `verify`, `poll`, `setSettings`, `quest`, `profile`.
- `Facts.scripts` — тексты скриптов, чтобы заметить подмену скрипта тестов (V = 0,8).

## Решения при реализации

- Адаптация (§7.6) применяется только к Testing. Буквальное правило (все категории) опустошает доски, которые ждут
  §7.7 и §10: у маленького проекта статы здоровья около 100 при любой одной находке. Теперь у магазина на доске три
  Easy-квеста и эпик, как в примере спека; у бота есть все пять ботовых квестов. Вернуть буквальное правило —
  расширить `ADAPTED_CATEGORIES` в `game/quests/board.ts`.
- Квест, выданный до разрешения команд, не получает условий со звёздочкой (решение этапа 7); XP за него с зелёным
  запуском тестов по `no_regressions` всё равно 100%.
- Журнал пишется раньше состояния: при сбое между ними XP не совпадёт с журналом и состояние восстановится из него.
